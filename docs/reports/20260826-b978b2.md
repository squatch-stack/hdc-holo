# Fusing cell_decode: 1.9x, and why it isn't 5x

Follow-up to the previous report. `cell_decode` is now fused; the pipeline is at
**6.92 s** end to end. The interesting part is why this fusion paid less than the
readout one, and what that says about the next step.

## Where the pipeline stands

| | wall |
|---|---|
| upstream NumPy, validate | ~22 min |
| CUDA backend, validate | 118 s |
| production mode (no ground truth) | 13.1 s |
| + binned decode_slice | 8.25 s |
| **+ fused cell_decode** | **6.92 s** |

Current stage breakdown: encode 2.78s, slices 0.70s, mip encode 1.83s,
x-ray 0.29s.

## The kernel

`cell_decode` was the last piece on the cuBLAS path. The design constraint was
load balance, not arithmetic. Measured distribution on the Tucson slice:

| band | cells | points/cell (min / med / max) |
|---|---|---|
| xfine | 1157 | 35 / 140 / 157 |
| fine | 751 | 99 / 283 / 296 |
| mid | 55 | 1716 / 2223 / 2853 |
| coarse | 2 | 14007 / 14007 / 14007 |

One block per cell - the obvious mapping - would give the coarse band **2 blocks
for 28,014 points** while xfine gets 1,157 blocks for ~140 each. That is exactly
the imbalance the 3DGS rasterizer paper (`arXiv:2308.04079`) flags. So each
cell's points are split into **bounded subproblems** of 128, the bin-then-split
structure from cuFINUFFT (`arXiv:2102.08463`), and no block ever carries more
than 128 points regardless of cell density.

Weights stream through shared memory in tiles of 128 frequencies; phase and
`sincos` are computed in registers; results land via `atomicAdd`, which is
required anyway because a point can belong to several cells and is a useful
side-effect: the result is order-independent.

| | time | speedup |
|---|---|---|
| unfused (cuBLAS) | 0.412 s | 1.00x |
| fused | 0.217 s | **1.90x** |

Agreement with the unfused path: 2.5e-06 relative, which is fp32 accumulation
order, not a defect.

## Why 1.9x and not 5.5x

The readout fusion got 5.5x. This one got 1.9x, and the reason is a real
structural difference rather than a worse kernel.

```
(cell, point) pairs : 500,196
distinct points     :  50,176
cells per point     :      10.0
```

Within a band, `freqs` is shared across every cell. The **unfused** path exploits
that: it computes `cos(p·W)` and `sin(p·W)` once per point per chunk and reuses
the planes across all ten cells that point belongs to. The **fused** kernel
recomputes phase and `sincos` per *pair* - roughly **10x the trig work** - and
still wins 1.9x purely by eliminating the memory traffic.

So the fusion is trading redundant compute for saved bandwidth, and winning, but
leaving most of the theoretical gain on the table.

## The next step this implies

Invert the mapping. Instead of one block per (cell, point-tile), make it one
block per **point-tile**, iterating over the union of cells those points touch,
with `cos/sin` held in registers across the whole cell list. Points in a tile are
spatially adjacent on a slice grid, so their cell lists overlap heavily - the
same locality binning already relies on.

That would recover the ~10x redundant trig while keeping the bandwidth win. It is
a bigger rewrite: the per-block cell set becomes dynamic, and shared-memory
residency for several cells' weights needs care. **Estimated, not measured** -
I will not put a number on it without a prototype.

## Verification

- hdc-holo suite with binning + both fused kernels: **56 passed, 4 skipped**
  (baseline 54 passed / 6 skipped).
- Fused vs unfused `cell_decode` on the real slice, all four bands: max 2.5e-06
  relative.
- Nothing upstream edited; everything is patched at import from `holo_cuda.py`
  and `holo_bin.py`.

## Honest status of the whole effort

Three of the four things tried helped, and the two largest wins came from
profiling rather than from the optimisation I expected to matter:

- **TF32**: no gain, slightly worse error. Abandoned.
- **Fused readout**: 5.5x on the kernel, ~0 on the pipeline.
- **Binning** (the unglamorous one): removed 82% of `decode_slice`, 19x on that step.
- **Skipping ground truth**: the single biggest lever, 118 s -> 13.1 s, and it
  is not an optimisation at all - it computes strictly less.
