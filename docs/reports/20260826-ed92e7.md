# Speeding up hdc-holo on the 5090: what actually mattered

Three optimisation attempts, two of which were aimed at the wrong thing. The
pattern each time was the same: the intuitive target was not the bottleneck, and
only profiling found the real one.

## Where the pipeline stands

| stage | before | after | note |
|---|---|---|---|
| upstream NumPy, validate | ~22 min | — | the published baseline |
| CUDA backend, validate | 118 s | 122 s | ground truth dominates |
| CUDA, production mode | — | **13.1 s** | skips ground truth entirely |
| **+ binned decode_slice** | — | **8.25 s** | current |

Production-mode breakdown now: encode 2.65s, slices 0.84s, mip encode 1.82s,
x-ray 0.73s.

## Attempt 1 — TF32: no gain, measurable loss

TF32 is the fp32 default for matmul on Blackwell. A pure-GEMM microbenchmark
showed 49x over NumPy with it on, versus 25x off. On the real scene:

| | TF32 off | TF32 on |
|---|---|---|
| wall | 118.2 s | 119.0 s |
| top-down slice err | 0.350 | 0.369 |
| x-ray (1,0,1) err | 0.395 | 0.396 |

**No speedup, slightly worse error.** Strictly dominated. The reason turned up in
the next profile: the GEMM is only ~30% of the kernel, so making it 2x faster
moves almost nothing.

The tensor-core precision-emulation literature (Ozaki scheme, EmuGEMM,
`arXiv:2203.03341`) is real and good work, but it targets that same 30%. I would
have chased it if I had not profiled first.

## Attempt 2 — fused readout kernel: real, but not where it counts

Profiling one readout chunk:

```
phase (P@W.T)   1.31 ms      trig  57%
cos             2.95 ms      GEMM  30%
sin             2.82 ms
2 GEMMs         2.96 ms      ~8 GB memory traffic
full chunk      9.86 ms      for inputs totalling ~1.5 MB
```

The kernel is memory-bound materialising a 2 GB phase matrix and two 2 GB trig
planes that nothing needs to see. A fused CUDA kernel computing phase, `sincos`
and the accumulation in one pass:

| | time | speedup |
|---|---|---|
| unfused (cuBLAS) | 0.161 s | 1.00x |
| fused kernel | 0.029 s | **5.54x** |

Real and it ships. But it did **nothing** for the scene pipeline, because that
pipeline spends its time elsewhere.

**A correction on accuracy.** I first measured the fused kernel as 8x *more*
accurate than cuBLAS. That does not generalise. It used all-positive `rand`
weights, where the sum accumulates coherently and cuBLAS's linear error growth
shows. On the real payload, with zero-mean weights, cancellation dominates and
both land at 1.48e-05. The fusion is a speed win only.

## Attempt 3 — the actual bottleneck: an O(cells x points) scan

`decode_slice` builds its cell/point pairs like this, per band:

```python
pairs = [(cell_mask(points, k, cell, reach), b) for k, b in bundles[name].items()]
```

`cell_mask` is a distance-to-AABB test over **all** points, run once per cell.
On the Tucson scene that is 2,621 cells x 50,176 points = **131.5M distance
evaluations in NumPy, per slice**. Measured:

```
CPU mask build + .any()     1.99 s     <- 82%
GPU cell_decode             0.44 s     <- 18%
```

The GPU work I was about to optimise was 18% of the call.

### The fix, from the literature

Both cuFINUFFT (`arXiv:2102.08463`) and the 3DGS rasterizer (`arXiv:2308.04079`)
solve this exact shape - overlapping AABB tests producing point/cell pairs - by
binning rather than scanning: emit one key per overlap, sort, derive per-cell
ranges.

The predicate is local. A point can only satisfy it for cells within
`r = ceil(reach / cell_size)` of its own cell, and **r = 1 for every band**:

| band | reach/cell | r | candidates |
|---|---|---|---|
| xfine | 0.38 | 1 | 27 |
| fine | 0.77 | 1 | 27 |
| mid | 0.48 | 1 | 27 |
| coarse | 0.60 | 1 | 27 |

So the candidate set is 27 cells, not 2,621.

| | time |
|---|---|
| mask scan | 2.09 s |
| binned | 0.11 s |
| | **19x** |

**Equivalence is checked, not argued.** The binned pair set is compared
cell-for-cell and index-for-index against `cell_mask` on the real scene, across
all four bands: identical.

## Bugs found along the way

- **hdc-holo's own tests caught mine.** `test_hdc_module_shims_resolve_to_holo_objects`
  failed because `holo/backend.py` and `hdc/accel.py` bind function objects at
  import time - patching `holo.accel` alone left the facades on the NumPy
  originals. Anything routed through a facade would silently have missed the GPU.
- The first binning implementation hardcoded 3 dimensions and broke on the 2-D
  cells the capture tests use. Also caught by their suite.
- On the runner side: `systemctl show` invents `Result=success` for a unit it
  cannot find, and transient units auto-GC on exit - so a **failed** job was
  being recorded as done. systemd now writes the outcome via `ExecStopPost`.

## What is left

- **`render_xray` still scans.** It uses `_cell_uv_mask`, a different predicate,
  and costs 0.73 s - worth binning only if x-ray becomes the target.
- **`cell_decode` is still unfused.** Now that binning removed the CPU cost, the
  GPU work is the larger share of the slice stage again. This is the one place
  the fused-kernel approach would now pay.
- **cuFINUFFT type-3** remains the untested large swing: the readout is
  mathematically a type-3 NUFFT. Arithmetic looks favourable (a 19^3 internal
  grid) but it would be spreading-dominated, and I will not claim a number
  without a prototype.

## Verification

- hdc-holo suite with binning + fused kernels: **56 passed, 4 skipped** (baseline
  is 54 passed / 6 skipped; the two extra are GPU-gated tests that only run when
  a backend is present).
- `holo-bench` cross-backend checksums, cupy vs numpy: `check_bundle_sum`
  4.5e-08, `check_readout_sum` 5.1e-08 - both inside the repo's 1e-7 bar.
- Nothing in the upstream repo was edited. All changes are patches applied at
  import time from `holo_cuda.py` / `holo_bin.py`.
